# 开发与交付流程

本流程适用于源码、测试、文档和打包修改。项目规则入口为 [AGENTS.md](../AGENTS.md)，职责与依赖见 [架构说明](architecture.md)，界面验收见 [UI 规范](ui-guidelines.md)。

## 1. 确定范围

- 阅读相关模块、测试和现有文档，查看 `git status --short` 与实际差异，保留用户已有修改。
- 较大功能和多文件重构先提出范围、实施步骤、兼容性及验收方式，得到确认后实施；已批准的范围无需反复确认。
- 修复先复现症状、定位原因，再做必要修改。文档补全等范围明确的任务直接执行。
- UI 改动先制作可批注的浏览器预览；用户确认后再修改实际程序。

## 2. 实施修改

- 遵守架构中的职责边界；底层命名和文件操作不依赖 Qt，界面控件只在主线程访问。
- 修复不夹带无关重构。删除代码前检查调用、动态入口、测试、`.spec` 资源及启动脚本引用。
- 重构保持命名顺序、扩展名处理、预检、不覆盖、失败回滚及撤销边界不变；行为变更单独说明。
- 行为缺陷优先补充可复现的回归测试。纯文档和低影响样式修改不为了数量添加测试。
- 修改职责或用户行为时，同步更新对应文档；临时预览、日志和截图放在忽略目录 `artifacts/`。

## 3. 验证

从仓库根目录执行 PowerShell 命令：

```powershell
# 常规测试：包含后台模式的 Qt 测试
& .\.venv\Scripts\python.exe -m unittest discover -s tests -v
# 原生测试：独立进程，需要 Windows 桌面
& .\.venv\Scripts\python.exe tests/test_native_ui.py --run
# Python 编译检查与差异格式检查
& .\.venv\Scripts\python.exe -m compileall -q renamer tests
git diff --check
```

| 修改范围 | 必要验证 |
| --- | --- |
| 仅文档 | 核对命令、路径、链接和实际实现；无需运行应用测试 |
| 命名、状态、执行或恢复 | 对应回归测试；交付前运行完整常规测试，文件操作只用临时目录 |
| UI、字体、焦点或窗口布局 | 相关常规测试、原生测试，以及批准预览与实际程序的视觉对照；拖放改动还应验证文件加入、顺序同步及编号变化 |
| 构建配置或发布包 | 构建测试、实际打包及新包启动验收 |

记录实际执行结果、跳过项和未验证项。普通测试会跳过原生测试，不能将跳过项算作通过；程序进程存在也不能证明窗口或交互正常。

跨重启恢复测试应使用临时目录中的 `RecoveryStore`，覆盖最近批次撤销、文件移动前后中断、损坏记录、文件身份不匹配，以及失败回滚重启后继续处理；不得读取或改动用户真实文件。

## 4. 打包与验收

需要交付可运行版本时，在 Windows x64 环境执行：

```powershell
& .\.venv\Scripts\python.exe -m pip install -r requirements-build.txt
& .\.venv\Scripts\python.exe build.py
```

- 打包前检查 `dist/latest/`、`dist/previous/` 中的程序是否正在使用。若在使用，请用户完成撤销或恢复后关闭；不得强制结束其会话。
- `build.py` 会先在 100%、125%、150%、200% 四档缩放下运行原生测试，需要可用的 Windows 桌面；任一检查失败即停止，不进入打包或版本轮换。
- 使用 `build.py` 完成临时构建及版本轮换；只保留 `latest/`、`previous/` 和最新 ZIP。失败时先检查日志与现有包，避免手工清空目录。
- 从项目目录之外启动新 EXE，检查实际窗口、中文字体和图标。用临时文件完成预览、确认改名、撤销，再检查原文件名及内容恢复。
- UI 变更还需完成 UI 规范中的视觉检查。交付整个应用文件夹或 ZIP，不能只复制 EXE 而丢弃 `_internal/`。
- 遇到“拒绝访问”时检查新包路径及权限，只修复必要范围，不修改整个工作盘的权限。

## 5. 提交与交付说明

- 未获授权不提交、不推送；需要提交时先检查实际差异，再按明确文件路径暂存，核对暂存内容。
- 提交消息使用中文 Conventional Commits，例如 `fix(ui): 修复文件名选区丢失`。不使用强制推送，不修改 Git 配置。
- 提交源码、必要资源、测试和维护文档；排除虚拟环境、EXE、ZIP、缓存、构建输出和临时验收材料。
- PR 说明修改目的、主要变化、实际验证和风险；UI 改动附必要的对照截图，只有真实存在的关联事项才链接 Issue。
- 交付时说明完成内容、验证结果、可运行包位置及尚存限制，不以“构建成功”替代功能或视觉验收。
